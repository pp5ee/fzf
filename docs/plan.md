## Goal
基于 workspace 中现有代码完成项目调研，梳理 Go 与 Rust 的转写现状，并制定一份面向“补齐未完成 Go→Rust 转写”的可执行实施计划。

## Context
用户已明确说明项目代码位于 workspace 中，需要通过阅读现有代码来回答模块划分、完成度、类型形态与测试现状等问题。因此，本计划不再把“请提供代码/目录”作为前置条件，而是将**代码扫描与现状识别**纳入计划的首个必做阶段。

本计划在保留原有“先调研、后实施、再验证”的主线基础上，进一步明确以下原则：

- 以 workspace 中的实际代码结构为准，识别 Go 与 Rust 两侧模块映射关系
- 先回答“项目是什么、已有多少 Rust 转写、还缺什么”，再进入编码补齐
- 以**模块/包/服务能力**为单位建立差异表，而非仅按文件数量统计迁移进度
- 若 Go 与 Rust 已同时存在测试或样例，应优先将其作为行为对齐基线
- 若发现 Rust 侧已有部分实现但语义不一致，则视为“部分完成待校正”，不能简单记为完成

调研阶段应至少覆盖以下内容：

- workspace 的目录结构、构建入口、语言分布与仓库形态（库 / CLI / 服务 / 多模块仓库）
- Go 源码中的核心模块、公共数据结构、对外接口、配置与运行入口
- Rust 工程中的 crate/module 组织、已实现功能、占位代码、TODO/FIXME/WIP 标记
- Go 与 Rust 两侧在 API、序列化、错误处理、并发模型、日志、配置上的差异
- 现有测试、样例数据、脚本、CI 配置及其是否可作为迁移验收基线

## Acceptance Criteria
- AC-1: 完成对 workspace 的项目结构调研，并输出项目类型、模块边界、构建入口与语言分布说明。
- AC-2: 输出一份 Go 与 Rust 的模块级映射清单，标明每个模块的状态为“已完成 / 部分完成 / 未开始 / 已实现但待验证”。
- AC-3: 对每个未完成或存在偏差的 Rust 转写模块，明确其 Go 源位置、Rust 对应位置、依赖关系、外部接口、主要风险与建议优先级。
- AC-4: 制定分阶段实施计划，至少包含“现状扫描”“差异确认与架构对齐”“核心转写补齐”“验证与收尾”四个阶段。
- AC-5: 计划中明确 Go 特性到 Rust 的映射策略，至少覆盖并发模型、错误处理、数据结构/所有权语义、序列化协议、配置与日志。
- AC-6: 若 workspace 中存在测试、样例或 CI 配置，计划需说明如何将其用作 Rust 转写验收基线；若缺失，则需将补齐最小验证集纳入计划。
- AC-7: 对无法一比一转写的能力，计划需标注替代实现方案、兼容性影响与回归验证要求。
- AC-8: 输出的实施计划需明确每阶段交付物，例如差异矩阵、迁移看板、模块任务清单、测试补齐清单、兼容性验证清单。
- AC-9: 在未完成代码扫描前，不直接承诺具体业务模块的实现细节；在扫描完成后，应能明确优先迁移范围和验收路径。

## Implementation Notes
- 第一阶段必须是**workspace 代码勘察**，目标是用代码事实回答原先开放问题，而不是继续停留在假设层。
- 建议先从以下线索建立项目认知：
  - 根目录下的 README、Makefile、go.mod、Cargo.toml、workspace 配置
  - CI 配置文件（如 GitHub Actions、GitLab CI、脚本目录）
  - Go 与 Rust 入口文件、主模块、公共库目录
  - TODO/FIXME/WIP/UNIMPLEMENTED 标记
- 建议输出一份“Go→Rust 功能映射矩阵”，每行至少包含：
  - 功能/模块名称
  - Go 位置
  - Rust 位置
  - 当前状态
  - 依赖项
  - 对外接口
  - 数据模型差异
  - 风险级别
  - 验收方式
- 模块优先级建议按以下顺序判断，而不是仅按代码量：
  1. Rust 已有框架但功能缺口明显的模块
  2. 被其他模块依赖的基础库/公共模型
  3. 对外暴露 API 或关键 CLI/服务入口
  4. 并发、网络、序列化、系统调用等高风险模块
- 对 Go 到 Rust 的关键映射需重点核查：
  - goroutine/channel/context → Rust async runtime、thread、channel、cancellation 策略
  - Go `error` 与多返回值 → Rust `Result`、错误枚举、错误传播链
  - interface / reflection / 动态分发 → trait / enum / 泛型 / 类型擦除方案
  - slice/map/零值语义 → Rust 集合类型、默认值、可选值与所有权边界
  - JSON/YAML/Protobuf/自定义协议 → Rust 序列化库与字段兼容性
  - I/O、网络、系统调用、CGO 或 unsafe 相关实现 → Rust 替代库与平台约束
- 验证策略建议采用“由浅入深”的方式：
  - 先跑通现有构建与测试，确认可执行基线
  - 再建立 Go 与 Rust 的行为对比样例
  - 对缺少测试的模块补黄金样例、快照测试或接口级回归测试
  - 对关键路径增加集成测试，必要时加入 benchmark 或资源占用对比
- 若扫描结果显示项目是多模块仓库，应为每个子项目分别建立迁移状态，而不是合并成单一结论。
- 若扫描结果显示 Rust 版本已偏离 Go 版本架构，应优先定义“行为兼容优先”还是“Rust 原生化优先”的边界，再决定是否接受非一比一实现。

## Out of Scope
- 在未完成 workspace 代码扫描前，直接进入全面编码或承诺具体模块已可转写完成
- 未经确认就重构整体架构、修改产品目标或重定义对外 API
- Go 与 Rust 之外其他语言版本的迁移规划
- 与“补齐未完成 Go→Rust 转写”无关的新功能设计
- 在缺乏测试和基线时，直接承诺 Rust 版本性能一定优于 Go 版本
- 在尚未核实兼容要求前，预先锁定最终接口变更或发布策略
