## Goal
将现有项目完整迁移为 Rust 版本，在 Ubuntu 环境下保持原有功能不变，并完成可运行验证与测试。

## Context
用户希望对“当前项目”进行纯语言层面的重写：从现有实现迁移到 Rust，但不改变业务功能、行为表现和对外接口预期。  
当前需求强调：
- **功能不变**：迁移后应与原项目在核心逻辑、输入输出、行为结果上保持一致。
- **仅做语言迁移**：不主动引入新功能、架构重构或产品层面的改动。
- **完成测试**：迁移完成后需要进行验证，确认 Rust 版本可用。
- **Ubuntu 环境运行**：需确保在 Ubuntu 上可以编译、运行和测试。

由于当前未提供项目代码、技术栈、目录结构、依赖、构建方式或测试基线，因此计划需基于“先梳理原项目，再等价迁移”的方式推进。

## Acceptance Criteria
- AC-1: 明确梳理原项目的模块结构、功能边界、外部依赖、构建方式及运行入口。
- AC-2: Rust 版本覆盖原项目的全部核心功能，不主动删减或新增业务能力。
- AC-3: Rust 实现的输入输出、接口语义和关键行为与原项目保持一致，至少对主要使用场景完成对照验证。
- AC-4: 在 Ubuntu 环境中可成功完成 Rust 项目的依赖安装、编译与运行。
- AC-5: 为 Rust 版本补充或迁移必要测试，包括单元测试、集成测试或端到端验证中的适用部分。
- AC-6: 提供清晰的运行与测试说明，确保他人可在 Ubuntu 上复现构建和验证流程。
- AC-7: 若原项目已有测试用例或样例数据，Rust 版本应复用这些基线进行行为一致性校验。
- AC-8: 迁移过程中不引入与“语言迁移”无关的功能性变更，除非为兼容 Rust 或 Ubuntu 所必需。

## Implementation Notes
- 首先需要对原项目进行**静态梳理**，识别：
  - 入口程序与模块划分
  - 配置文件与环境变量
  - 第三方依赖与系统依赖
  - 数据模型、协议、文件格式、网络接口
  - 现有测试、示例、基准输出
- Rust 迁移建议遵循**等价替换**原则：
  - 保持原有模块职责尽量一致，便于映射与回归验证
  - 优先保证行为一致，而不是追求 Rust 风格的激进重构
  - 对外接口（CLI 参数、HTTP API、文件输入输出、消息格式等）尽量保持兼容
- 工程实现上通常需要：
  - 使用 `cargo` 管理依赖和构建
  - 根据项目类型选择合适生态，例如：
    - CLI：`clap`
    - Web/API：`axum` / `actix-web`
    - 异步：`tokio`
    - 序列化：`serde`
    - 数据库：对应 Rust 驱动或 ORM
- 测试策略应以**行为对齐**为核心：
  - 若原项目已有测试，优先迁移或复用测试数据
  - 若没有测试，需要先从原实现中提取关键样例作为黄金样本
  - 对关键路径做输入输出比对，确保“功能不变”
- Ubuntu 适配需要关注：
  - Rust toolchain 安装方式（如 `rustup`）
  - 系统库依赖（如 OpenSSL、SQLite、编译工具链等）
  - Shell 脚本、路径分隔符、权限与文件系统差异
- 若原项目依赖某些动态语言特性、反射机制、运行时热加载、特定 C 扩展或平台相关行为，Rust 迁移复杂度会明显提升，应提前评估。
- 交付建议包含：
  - Rust 源码
  - `Cargo.toml`
  - Ubuntu 下的构建与运行说明
  - 测试说明
  - 与原项目行为对齐的验证记录

## Out of Scope
- 主动新增业务功能或产品能力
- 在无必要前提下重构原有业务流程或重新设计系统架构
- 将项目同时适配除 Ubuntu 之外的其他操作系统
- 性能优化、并发重写、安全加固等非“语言迁移必需”的专项改造
- UI/UX 重新设计
- 替换原有外部服务、协议或数据契约，除非原依赖在 Rust/Ubuntu 下无法兼容且必须调整
- 部署到生产环境、CI/CD 流水线改造或运维体系建设（除非用户后续明确要求）
